Kimi: Reviewed both full PRs at the pinned heads, the fork via compare API, and the relevant NT source at 6be5a50. Findings only.

   PR-A — SBE schema 3:5 (head 1cd8349)

   A1 — Real but latent: depth/trades REST decoders can now mis-decode a future bumped fixed block instead of erroring. (Non-blocking for Bolt's current
   surface.)

   The port deletes the exact-version gate in MessageHeader::validate (fork:crates/adapters/binance/src/spot/http/parse.rs, validate() now checks only
   schema_id != SBE_SCHEMA_ID; the version != SBE_SCHEMA_VERSION → VersionMismatch branch is gone). For decode_exchange_info that is fine — groups are
   self-delimiting and the symbol item length is pinned (parse.rs:964 symbols_block_len != SYMBOL_BLOCK_LENGTH → loud InvalidBlockLength), and that is the
   only REST path Bolt exercises. But decode_depth (parse.rs:149-184) and decode_trades (parse.rs:194-224) read their fixed block at fixed offsets
   (last_update_id/price_exponent/qty_exponent) and then call read_group_header() immediately, never consulting the runtime header.block_length. The PR's own
   README (spot/sbe/README.md, "Version compatibility") concedes exactly this.

   Concrete scenario: Binance ships schema 3:6 that appends one field to the depth or trades message fixed block (the part before the repeating group). The
   runtime block_length grows, but header.validate() no longer rejects it, so the body decoder reads the appended fixed-field bytes as the group header
   (block_len, count). Outcome is a garbage count → either a silently corrupt order book/trade list fed downstream, or read_group walking off the buffer.
