Findings
F1 — MEDIUM: Unbounded audit history growth can brick routine state persistence and trigger history-destroying invalidate()
Anchor: src/bolt_v3_kill_switch_store.rs:121-135 (write_state_with_loss_snapshot + existing_loss_governor_manual_recoveries); cascade into src/bolt_v3_loss_protection.rs:725-727 (persist_failed_state_or_invalidate).
Scenario: Each KillSwitchLossGovernorManualRecoveryRecord serializes to ~250-350 bytes in pretty JSON. With the production default max_state_file_bytes = 65_536 (confirmed in test fixture and KillSwitchConfigBlock), approximately 200 recovery records saturate the limit. There is no rotation, pruning, or compaction mechanism.
Once saturated:
1. write_loss_governor_manual_recovery fails ensure_state_bytes_within_limit → StateTooLarge.
2. The fallback write_state_with_loss_snapshot(FailedManualIntervention, ...) also calls existing_loss_governor_manual_recoveries() which loads the same full history → also fails StateTooLarge.
3. In the runtime path, persist_failed_state_or_invalidate (loss_protection.rs:725) catches the write_state failure and calls self.store.invalidate(), which writes b"!" — destroying the entire audit history. This directly violates the claimed "history never deleted" guarantee under this cascading failure.
The brick is persistent: the store remains near-limit, and any future routine state write (new position PnL entry, halt action) can push it over. There is no operator tool or documented procedure to prune the history.
Recommendation: Either (a) exclude loss_governor_manual_recoveries from ensure_state_bytes_within_limit (audit history should not count against the safety-state byte budget), or (b) add bounded retention (e.g., keep last N records), or (c) add a documented operator procedure + tool to export-and-prune. Option (a) is the cleanest separation of concerns.
F2 — MEDIUM: Concurrent node + offline recovery can silently lose audit records (TOCTOU); posture undocumented in CLI
Anchor: src/main.rs:172-183 (clap variant with no about); src/bolt_v3_kill_switch_store.rs:121-135 (read-modify-write without locking).
Scenario: The command assumes the node is stopped (documented only in the PR description, not in --help). If violated:
T1  Node: write_state_with_loss_snapshot enters
T1a Node: existing_loss_governor_manual_recoveries() reads store → gets OLD history (N records)
T2  Recovery: write_loss_governor_manual_recovery atomic-renames → store now has N+1 records
T1b Node: serialize(state, snapshot, OLD N records) → atomic rename → overwrites T2
Result: the recovery's audit record is silently lost. The node carried forward the pre-recovery history. The node's subsequent state write is fail-safe for trading state (it re-evaluates and may re-halt), but the audit trail has a gap.
The window is the entire write_state_with_loss_snapshot call (read → serialize → rename). There is no file lock, PID check, or advisory mutex.
Note: InitKillSwitchStore has the same undocumented offline posture, but the consequence there (store already exists → StateAlreadyExists error) is self-protecting. Here, the consequence (silent audit gap) is not.
Recommendation: Add #[command(about = "Record a loss-governor manual recovery (requires stopped node)")] or equivalent to the clap variant. Consider a PID-file or lockfile check to detect a running node and refuse.
F3 — LOW: Recovery impossible when stored daily_realized_pnl still breaches; RecoveryRefused gives zero diagnostic
Anchor: src/bolt_v3_loss_governor_manual_recovery_ops.rs:280-289 (manual_recovery_loss_snapshot); :107 (RecoveryRefused Display).
Scenario: manual_recovery_loss_snapshot constructs a synthetic LossSnapshot using the stored daily_realized_pnl for both daily_pnl and rolling_pnl. If the halt was triggered by a daily loss breach, the stored value still breaches → evaluate_loss_admission returns accepted: false → next_loss_governor_manual_recovery_trading_state returns None → RecoveryRefused.
The command cannot clear its primary use case (actual loss-breach halt) unless the runtime updated the stored PnL post-halt — which can't happen when the node is stopped. The error message ("loss-governor manual recovery refused by the recovery state machine") doesn't distinguish between staleness refusal, loss-breach refusal, evidence refusal, or recovery-mode refusal. An operator cannot self-diagnose.
Additionally, rolling_pnl = daily_realized_pnl is a semantic substitution: if max_rolling_loss < max_daily_loss, a daily PnL within the daily limit can spuriously trip the rolling check, producing a confusing refusal.
Assessment: Fail-closed (safe), but functionally limits the command to stale-snapshot halts and halts where the stored PnL has been refreshed by a prior runtime cycle. This is a faithful implementation of the existing next_loss_governor_manual_recovery_trading_state contract — the design question of whether manual recovery should override a still-breaching loss is a product decision. But the opaque error is a usability defect in a safety-critical command.
F4 — LOW: Halting state recovery path untested
Anchor: src/bolt_v3_loss_governor_manual_recovery_ops.rs:236-256 (recoverable_current_state) + :262-276 (loss_governor_recoverable_trading_state).
Scenario: All four new tests use KillSwitchState::Halted. The Halting variant takes a distinct code path: load_recovery_record classifies it as FailClosed { reason: UnresolvedHalt, state: Some(...) }, which recoverable_current_state extracts via the UnresolvedHalt arm. This arm is exercised in production but has no test coverage. Recovery from Halting (halt actions possibly incomplete) is the riskier variant and most deserves coverage.

The core safety contract is sound: no forked state machine, evidence is validated before any I/O, fail-closed posture on every store error class, schema compatibility works both directions, and the history-preservation regression test genuinely exercises the Err branch.    Findings

   1. High — production loss-governor halt never populates
   loss_halt_reason

   • Anchor: src/bolt_v3_loss_protection.rs:436
     (halt_for_realized_loss_breach)
   • Scenario: The only production code path that creates a
     loss-governor kill-switch halt still calls
     KillSwitchHaltTrigger::loss_governor_breach(source,
     observed_at_unix_nanos, LOSS_TRIGGER_REASON) — the
     constructor that leaves loss_halt_reason as None. Every
     real production halt is therefore treated as a legacy
     store by
     next_loss_governor_clock_verified_manual_recovery_trading
     _state, which returns LegacyStoreMissingTriggerReason and
     refuses offline recovery.
   • Consequence: the advertised A2 offline recovery for
     DailyLossLimit (and RollingLossLimit) does not work on
     real stores. The passing day-rolled/rolling-elapsed tests
     work only because
     persist_loss_governor_halted_state_with_reason injects
     the reason field after writing the state. The fix is a
     one-line change to loss_governor_breach_with_reason(...,
     LossHaltReason::DailyLossLimit).

   2. Medium — rolling-window duration is current-config, not
   durable with the trigger

   • Anchor: src/bolt_v3_loss_halt_actions.rs:370-374
   • Scenario: For a RollingLossLimit halt, the elapsed check
     uses rolling_window_ns from the freshly loaded config
     (loss_governor.rolling_window_ns). If an operator changes
     that window between the halt and recovery, the verdict
     changes retroactively. This is an asymmetric trust model
     compared with the daily check, which is purely
     clock-driven from the stored trigger timestamp.
   • Consequence: a shortened window can allow premature
     recovery; a lengthened window can deny legitimate
     recovery. Combined with finding #1, this branch is
     currently unreachable in production anyway.

   3. Low — some refusal paths are not audited

   • Anchor:
     src/bolt_v3_loss_governor_manual_recovery_ops.rs:317-324
     (invalid evidence) and :296-314 (missing/disabled config)
   • Scenario: An operator with structurally invalid evidence,
     or a config that disables kill-switch/loss-governor, is
     refused before any store interaction and no audit line is
     written. Unauthorized-operator and clock-refusal paths
     are audited.
   • Consequence: probing/refusal attempts in these pre-flight
     error classes leave no audit trail. The help/module docs
     do not document this boundary.

   4. Low — unbounded audit file with linear append/load cost

   • Anchor: src/bolt_v3_kill_switch_store.rs:208-266
     (loss_governor_manual_recovery_audit_appendable_line_coun
     t) and :168-206 (load_loss_governor_manual_recoveries)
   • Scenario: Every append does a full line scan; every load
     reads the entire file into memory. The file is documented
     as unbounded and externally rotated, but there is no size
     cap or rotation enforcement.
   • Consequence: over a long operational life, append latency
     grows linearly and a large audit file can cause memory
     pressure or OOM on load. No fail-closed safety issue, but
     an operational pitfall.

   5. Info — duplicated UTC-day constant

   • Anchor: src/bolt_v3_loss_halt_actions.rs:14 and
     src/bolt_v3_loss_protection.rs:24
   • Scenario: NANOS_PER_UTC_DAY = 86_400_000_000_000 is
     defined in two places. It is correctly allowlisted in the
     runtime-literal audit, but it is a minor DRY violation.

   Attack-area notes

   • UTC-day arithmetic: integer division by
     86_400_000_000_000 is correct for Unix-time UTC days;
     leap seconds are irrelevant. The “day rolled” check is
     strict (trigger_day < now_day), so same-day refusal is
     conservative.
   • Rolling-window check: uses now_ns -
     trigger_observed_at_ns > rolling_window_ns (strict
     greater), which is one nanosecond more conservative than
     an inclusive check.
   • Trigger-reason integrity: the store is already
     operator-writable file-system state; an operator with
     write access could forge loss_halt_reason. The runtime
     re-check backstop at the next node start limits the blast
     radius, so no new trust assumption is introduced beyond
     the existing store trust model.
   • Concurrency posture: documented correctly. The CLI
     appends audit first and then writes Armed; a running node
     could later overwrite the state file because it is
     last-writer-wins. Audit records are in a separate file,
     so they survive a node overwrite.
   • Clock trust: src/main.rs:714 uses SystemTime::now() for
     now_ns; the operator controls the host clock, which is
     the intended model for clock-verified recovery.
   • Red-proof deviation: no executed red proof this round.
     Probe runs 28715550336 and 28715857029 died with runner
     exit code 143. The differential claims (day-rolled would
     fail at round-2, torn-line would fail pre-fix) rest on
     code construction and the green test suite; they are
     plausible but not empirically exercised.

   The round-3 redesign is structurally sound: audit history
   is decoupled from the safety store, schema compat is clean,

LossGovernorManualRecoveryEvidence::new is constructed before the store is loaded.
