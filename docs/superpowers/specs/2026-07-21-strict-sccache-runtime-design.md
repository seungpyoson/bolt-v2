# Strict sccache Runtime Design

## Decision and scope

Build and publish a repository-governed sccache v0.16.0 derivative that removes silent cache bypasses. This is a standalone prerequisite task for PR #1494. It does not modify #1494, the Rust Probe OIDC boundary, advisory-run cancellation, or runner allocation.

This specification and the superseded implementation plan at `docs/superpowers/plans/2026-07-21-strict-sccache-runtime.md` are temporary implementation scaffolding. After implementation findings are resolved, both are removed before merge and the resulting code-only head receives fresh exact-head native/static verification and review. Lasting governed values and short operator explanations live beside their keys in `ci/sccache-strict.toml`; the later #1494 change places its real-toolchain, governed compiler environment, controlled-environment, and Clang default-config assertions beside the canonical compiler-path keys in `ci/sccache-location.toml`. The release workflow's own preflight failure messages explain the required immutable-release setting, protected environment, and orphan-state response without duplicating config values in a permanent design document or runbook.

The prerequisite PR owns:

- the exact upstream source identity and source archive digest;
- one in-repository patch containing the strict behavior and its upstream tests;
- one cacheless, reproducible ARM64/X64 build path;
- one protected same-repository GitHub release publisher;
- immutable release assets and their provenance manifest.

PR #1494 remains the adoption PR. After the prerequisite is merged and its assets are published, #1494 will pin the immutable release and per-architecture asset IDs and SHA-256 values, own the runtime timeout values, abstract-socket naming template, fresh strict-cache S3 prefix, exact canonical real-compiler paths paired with their expected Rust/GCC/Clang family, and the exact family-scoped governed compiler-environment values in `ci/sccache-location.toml`, deterministically derive a per-job-unique abstract name from that governed template and job identity, install those assets directly, validate its `active` input, and route Cargo-owned invocations through the governed wrapper using those paths rather than a wrapper, proxy, or search-path name. The same typed path/family and governed-environment values are supplied to the strict client and server: the client validates the raw compiler selector and complete raw environment before upstream path lookup or environment filtering, and the server revalidates the transmitted selector, expected family, and canonicalized compiler environment. #1494's reviewed configuration is the authority that each configured path and its subordinate compiler tools name the intended immutable toolchain rather than a transparent wrapper or proxy; finite family probes do not attest compiler contents. If #1494 requires cacheable Clang, its routing supplies `--no-default-config`, and its configured Clang must successfully accept that suppression in the fixed probe and representative cacheable invocation; absence or rejection remains correct but intentionally non-cacheable or fatal rather than being inferred from a hardcoded version floor. #1494 also owns job-environment control proving the governed toolchain search locations and configured compiler-semantic values cannot change during a job and provides controlled setup/runtime failure evidence. The cache-format revision itself remains single-homed in this derivative's build TOML and cache key; #1494 owns only the storage location and consumer values. Job-wide prevention of a build script or nested process invoking an unwrapped compiler belongs to #1494, not to this binary prerequisite.

## Runtime invariant

For every supported compiler invocation accepted by the governed wrapper, the binary enforces this contract without an environment-variable opt-out:

> Before any compiler-path lookup, raw-environment filtering, or request transmission, the strict client disables upstream compiler-named-symlink dispatch, validates the explicit raw compiler selector against the configured exact-path set, positively classifies the complete raw Unix environment of every governed Rust, GCC, and Clang request, and bypasses upstream search and filtering. Before emitting `CompileStarted`, the already-running governed server must independently revalidate that selector and canonical environment, finish request-boundary forced-mode rejection, governed-compiler family validation through a deterministic cleared probe environment, fail-closed byte-oriented raw-argument and raw-environment classification, and complete output classification under one absolute classification deadline. An asynchronous preflight returns exactly `Cacheable(hasher)`, truthful `NotCompilation`, typed `CannotCache(reason)`, or a fatal error. Only `Cacheable` may emit `CompileStarted` and enter hash generation, storage, or server compilation. Dedicated pre-start `NotCompilation` and typed `CannotCache(reason)` responses may authorize intentional client execution, preserving the original arguments, environment, stdin, and file descriptors while recording the classification and reason. Every pre-start child runs as leader of a dedicated process group with bounded output and a cancellation-safe supervisor that owns the group independently of the request future through bounded classification, termination grace, and post-kill cleanup. Confirmed live-group quiescence permits exact-child reap and later server reuse; cleanup uncertainty atomically enters a poison-pending state that blocks new response commits, closes the listener, cancels every accepted or in-flight request, and proceeds to terminal daemon poison instead of waiting without a bound or claiming reuse. One shared authority-response gate linearizes terminal poison with complete response-frame commitment: gate acquisition, bounded frame serialization and write, socket abort, and terminal transition all use the one existing absolute cleanup deadline; only an already-admitted frame whose final framed byte was accepted by the transport before the terminal transition may succeed, while every uncommitted or partially written response is closed and fails. The terminal transition occurs when poison acquires the gate, or at immediate process exit if the deadline expires first. At that deadline the process terminates nonzero without waiting for gate ownership or destructor cleanup. Merely dropping the classifier future or killing only the direct child is not cleanup. No connection failure, server restart, IPC error, EOF, unexpected response, cache read error or timeout, corrupt entry, operational inspection or staging failure, storage-capability failure, or required write failure may authorize compiler execution; each fails the invocation and invalidates the job.

The governed compiler set is Rust plus the pinned generic GCC-family C/C++ path used by GCC and Clang. At strict client entry, before `cmdline.rs` can reinterpret a compiler-named symlink or either client seam can call `which_in`, the strict derivative disables symlink dispatch and requires the explicit raw compiler selector to be an absolute byte-exact member of #1494's typed configured path/family set; a search-path name, relative path, symlink spelling, mismatched path, or other selector fails without lookup, canonicalization, connection, or client execution. The strict client bypasses `which_in` and transmits that exact path and expected family; the server requires the same byte-exact configured member before any probe or request parsing. It performs no per-request executable search, wrapper unwrapping, proxy resolution, or path canonicalization. Strict compiler verification clears the request and host environments and runs that configured executable with only family-specific fixed probe arguments under the TOML-declared deterministic `identity_probe_environment`; the configured Clang probe includes `--no-default-config`, while Rust and GCC receive only their own accepted fixed arguments. It never forwards request arguments such as `--compiler-bindir` or `-ccbin` or request variables such as `LD_PRELOAD`, `GCC_EXEC_PREFIX`, `COMPILER_PATH`, or `RUSTUP_TOOLCHAIN`. The probe verifies the configured compiler family under the governed environment; it does not prove that the configured file is not a transparent wrapper or proxy. A mismatch or non-governed family fails before request parsing, cache-key derivation, storage, or other request-specific compiler work. Probe failure is fatal. This closed set defines which cache-key hashers receive the strict format token and which parser seams the behavior matrix governs.

Destination classification uses one asynchronous pre-`CompileStarted` seam. Before compiler-specific parsing, one shared Unix-byte-oriented inspection examines the complete raw `OsStr` argv of every governed Rust, GCC, and Clang request. The first matching classification owns the typed reason: any separate argument whose first byte is `@`—including bare `@`, `@@file`, invalid-UTF-8 paths, value-position Rust argfiles, and the separate `@file` following `-Xclang`, `-Xassembler`, `-Xpreprocessor`, or `-Xlinker`—returns the typed semantic `CannotCacheReason::ResponseFile`; an embedded non-leading `@` does not. A GCC/Clang `-Wa,` or `-Wp,` payload containing embedded external `@file`, explicit Clang `--config`, `--config-user-dir`, or `--config-system-dir`, GCC `-specs=`, `-wrapper`, `-B`, or an otherwise-unhashed plugin/tool selector returns `CannotCacheReason::CompilerArgumentIndirection` under the same pre-parse rule. A Clang invocation lacking the exact `--no-default-config` argument returns that reason before compiler-specific parsing, so ambient user, system, or compiler-adjacent default configuration files can never influence a cacheable request; the earlier configured-family probe already used the same suppression, and the strict Clang table positively recognizes and keys the literal suppression flag. The strict C-family parser additionally changes the upstream unknown-flag default from pass-through to typed `CannotCache`: a flag remains cacheable only when the strict table proves it is literal-and-keyed, its referenced content is hashed, its effect is captured without external indirection, or it is inert in the accepted compile-only shape. Only the embedded `-Wl,@file` compile-only form remains an inert negative control; the separated `-Xlinker @file` form follows the family-total byte-leading rule and is deliberately non-cacheable.

The strict client captures the complete raw Unix environment before upstream `cmdline.rs` removes entries such as `LD_PRELOAD` and `SOURCE_DATE_EPOCH`. One shared code-owned, family-aware classification schema rejects duplicate byte names and classifies every entry of every governed Rust, GCC, and Clang request before the request proceeds. A request missing any family-governed TOML name is a mismatch returning typed `CannotCacheReason::CompilerEnvironment`; the classifier never fills an absent request value from configuration. Compiler-semantic inputs such as a governed `PATH`, locale, include search, `SOURCE_DATE_EPOCH`, or family-specific rustc control must exactly match the #1494 TOML-owned family-scoped governed name/value set, are forwarded to the applicable compiler, and are hashed in deterministic name order with an explicit present/absent tag and unambiguous length-framed name/value bytes. Compiler interposition or ungoverned search state such as `LD_PRELOAD`, `GCC_EXEC_PREFIX`, or `COMPILER_PATH`, a governed-name value mismatch or absence, and every unclassified entry return the same typed intentional classification. For C-family requests, code-proven GitHub runner metadata, Cargo/cc build-orchestration metadata, and AWS/GitHub credential classes ignored by the governed compiler and repository compile inputs are stripped from the request-derived child environment and never enter the cache key.

For Rust specifically, the shared schema admits only exact TOML-governed rustc-semantic values, code-owned source-visible classes whose use the pinned dep-info contract records, admitted `CARGO_*` classes already keyed by the pinned Rust hasher, and operational or credential classes proven not to be read by the pinned rustc itself. The admitted source-visible and operational/credential values are forwarded unchanged to rustc so `env!` and `option_env!` retain the original request semantics; if the crate reads one, the env-dep result must key its explicit presence state and length-framed exact value, distinguishing unset from present-empty, while an unread value does not churn the key. Admitted `CARGO_*` values retain their mandatory Rust-hasher keying under the same prefix-free encoding. Raw rustc-control or interposition state that is not guaranteed to appear in dep-info—most importantly `RUSTC_BOOTSTRAP`, which changes feature-gate behavior, and any compiler-affecting entry removed by upstream filtering—must be explicitly TOML-governed and separately keyed or else returns `CannotCacheReason::CompilerEnvironment`; `LD_PRELOAD` is always classified rather than governed. No value may rely on dep-info as authority for rustc's own environment reads, and an unknown Rust entry fails to intentional client execution rather than being silently forwarded.

The operational classification is a closed code/protocol semantic table proven against the repository's real build environment rather than a broad user-configurable allowlist; TOML owns only the exact permitted compiler-semantic values. The server independently reruns the same classification against the transmitted raw environment and constructs the family-specific canonical child environment rather than trusting upstream's filtered vector. No environment value is logged. Thus per-run IDs, build-orchestration state ignored by the governed real compiler, and short-lived credentials cannot churn C-family keys or reach C-family compiler children; the same values preserve Rust source-visible semantics and affect Rust keys only when env-dep proves that the crate read them. Every cacheable compiler-affecting byte in either family is governed and keyed or rejected to the original client execution path.

These typed variants are the sole protocol and telemetry authority; no TOML string or execution allowlist duplicates them. The server performs no classified named-file open, metadata query, expansion, subprocess, preprocessing, hashing, storage, or compilation before returning the dedicated classification, which authorizes exactly one client execution with the original arguments and environment. There is no helper process, cacheable argument-file implementation, or alternate expansion path. For requests that pass the fail-closed table, GCC-family parsers expose declared outputs to preflight so structural classification completes before `CompileStarted`, preprocessing, hashing, storage, or compilation.

Rust output filenames are not available at argument-parse time. The asynchronous preflight runs the pinned parser's existing read-only `rustc --print file-names` discovery query as the first request-specific subprocess, before any `CompileStarted` response, dep-info subprocess, source or extern hashing, storage, or other request-specific compiler work. Rust classifies output-directory and explicit-output constraints during parsing, treats `--print file-names` as governed classification work rather than compilation proper, and completes file-level duplicate, collision, and destination classification immediately after that query. The query shares the absolute classification deadline, process-group supervisor, and output-byte ceiling; expiry, cancellation, excess output, or child failure reaches either confirmed-quiescent exact-child reap or bounded daemon-poison termination before returning or closing with fatal failure. Discovery, operational metadata, or parent-inspection failure is fatal and never becomes `CannotCache`.

`NotCompilation` is reserved for invocations proven not to perform source preprocessing or compilation. A GCC-family driver invocation containing source input but lacking the cacheable compile-only shape—including compile-and-link—returns a typed semantic `CannotCache` such as `compile-and-link`; pure object/library link or other genuine non-compilation may return `NotCompilation`. Classification reasons are typed code/protocol semantics and telemetry, not selectable policy or an execution allowlist. Their wire identity is owned by the strict protocol revision rather than a duplicate TOML label.

Every client first performs a mandatory identity handshake. The server identity binds a derived identity of the exact source, patch, workflow, recipe, verifier driver, executor, toolchain, feature set, profile, and target, plus the strict protocol and compiler-environment-schema revisions, effective S3 configuration, configured mode, basedirs, configured canonical compiler path/family pairs, configured family-scoped governed compiler-environment values, all four governed consumer timeout values, the compiled-in maximum runtime timeout, classification timeout, termination-grace timeout, post-kill cleanup timeout, and output ceiling, deterministic identity-probe environment, and the governed IPC frame-size limit. An upstream, stale, differently built, or differently configured daemon is rejected before any compile or evidence request. Legacy `UnhandledCompile` keeps its upstream wire discriminant and is fatal; the intentional classifications use new appended discriminants whose typed reasons are protocol-owned.

The governed Linux derivative accepts only a Linux abstract Unix-domain socket supplied through the adoption configuration. Both client and server require a non-empty, successfully decoded name whose byte length does not exceed the TOML-owned, compiled-in `max_abstract_socket_name_bytes = 107`, derived from Linux `sun_path[108]` minus the leading abstract-namespace NUL. The strict address resolver has no pathname, TCP-port, or default-port fallback; missing, malformed, pathname, TCP, empty, or oversized values fail at strict entry before startup or connection. Abstract sockets have no filesystem inode or cleanup lifecycle: the kernel releases the name when the last reference closes. Server child-startup notification uses one inherited unnamed Unix socketpair, never a temporary pathname socket. This removes pathname ownership, stale-file recovery, lock-file replacement, quarantine, startup-notifier cleanup, and shutdown-unlink behavior from the governed contract.

The control boundary is the authority for execution, not merely the process that spawns rustc. An explicitly classified invocation is governed even when the client executes it: the server observed it, selected a typed path, and recorded the applicable reason before execution. A failure-induced fall-through is prohibited because no server classification authorized it.

This distinction is required by live evidence. Exact-head run `29814080045` reported 123 non-cacheable calls in `build` and 144 in `test`, including stdin-fed `-` invocations. The v0.16.0 request protocol transports arguments and environment but not stdin or inherited file descriptors. Moving these calls into the daemon would change their behavior or require a new stdin/FD transport protocol. The smaller complete fix retains intentional classified client execution and makes every failure path fatal.

## Exact upstream boundary

The derivative is based on sccache v0.16.0 at commit `b799af2eea02bba9e0ef2550775fe10296b62981`. The pinned source archive is:

- URL: `https://github.com/mozilla/sccache/archive/b799af2eea02bba9e0ef2550775fe10296b62981.tar.gz`
- SHA-256: `a4419b0a2278255d11eda1f76ee98efab0aec72649617bbefd24a5e92acf4af3`

The patch must close the complete observed class, not only the demonstrated EOF branch:

1. [`src/commands.rs`](https://github.com/mozilla/sccache/blob/b799af2eea02bba9e0ef2550775fe10296b62981/src/commands.rs#L302-L339) auto-starts a replacement server after connection refusal, and its [compile response handling](https://github.com/mozilla/sccache/blob/b799af2eea02bba9e0ef2550775fe10296b62981/src/commands.rs#L521-L577) starts the compiler after both an explicit `UnhandledCompile` response and `CompileStarted` followed by `UnexpectedEof`.
2. [`src/protocol.rs`](https://github.com/mozilla/sccache/blob/b799af2eea02bba9e0ef2550775fe10296b62981/src/protocol.rs#L38-L75) conflates `NotCompilation` and `CannotCache`, while the compile request carries no stdin or inherited file descriptors.
3. [`src/server.rs`](https://github.com/mozilla/sccache/blob/b799af2eea02bba9e0ef2550775fe10296b62981/src/server.rs#L1240-L1289) maps both classifications to that response and immediately emits `CompileStarted` for `CompilerArguments::Ok` before `CompilerHasher::generate_hash_key` runs. A structural classification discovered in the hasher is therefore too late to authorize the dedicated client path.
4. [`src/compiler/compiler.rs`](https://github.com/mozilla/sccache/blob/b799af2eea02bba9e0ef2550775fe10296b62981/src/compiler/compiler.rs#L576-L813) treats cache read errors, timeouts, and corrupt extracted objects as misses, and supports caller-forced no-cache/recache paths.
5. [`src/cache/cache.rs`](https://github.com/mozilla/sccache/blob/b799af2eea02bba9e0ef2550775fe10296b62981/src/cache/cache.rs#L210-L282) converts remote read errors into misses and can silently negotiate configured read-write storage down to read-only. Its [backend selection](https://github.com/mozilla/sccache/blob/b799af2eea02bba9e0ef2550775fe10296b62981/src/cache/cache.rs#L573-L613) permits multilevel storage and falls back to a local disk cache when no remote backend resolves.
6. [`src/cache/multilevel.rs`](https://github.com/mozilla/sccache/blob/b799af2eea02bba9e0ef2550775fe10296b62981/src/cache/multilevel.rs#L607-L715) suppresses individual backend read failures and continues to later levels.
7. [`src/cache/cache_io.rs`](https://github.com/mozilla/sccache/blob/b799af2eea02bba9e0ef2550775fe10296b62981/src/cache/cache_io.rs#L100-L195) can discard corrupt stdout/stderr data and treat corrupt optional outputs as absent.
8. [`src/server.rs`](https://github.com/mozilla/sccache/blob/b799af2eea02bba9e0ef2550775fe10296b62981/src/server.rs#L1517-L1526) records cache write errors but still returns the successful compiler result.
9. [`src/compiler/gcc.rs`](https://github.com/mozilla/sccache/blob/b799af2eea02bba9e0ef2550775fe10296b62981/src/compiler/gcc.rs#L1060-L1115) can turn response-file open or read failure back into an `@file` argument that later authorizes permissive local execution, while recursive expansion has no cycle, file-type, byte, depth, argument-count, or deadline bound. Even a validated regular-file read can block indefinitely on a stalled filesystem, so the strict derivative refuses every response-file invocation before opening it.
10. [`src/compiler/rust.rs`](https://github.com/mozilla/sccache/blob/b799af2eea02bba9e0ef2550775fe10296b62981/src/compiler/rust.rs#L1367-L1557) runs request-specific dep-info work before its late output-filename query, so strict output classification must reorder that query ahead of dep-info. Its output query and compiler identity probes await unbounded child output without governed kill-and-reap behavior.
11. [`src/commands.rs`](https://github.com/mozilla/sccache/blob/b799af2eea02bba9e0ef2550775fe10296b62981/src/commands.rs#L91-L102) uses a temporary pathname Unix socket for parent/child startup notification even when the runtime listener is abstract.
12. [`src/compiler/compiler.rs`](https://github.com/mozilla/sccache/blob/b799af2eea02bba9e0ef2550775fe10296b62981/src/compiler/compiler.rs#L1409-L1507) supplies request environment to Rust and C-family identity probes and wrapper/proxy resolution, while its [argument handling](https://github.com/mozilla/sccache/blob/b799af2eea02bba9e0ef2550775fe10296b62981/src/compiler/compiler.rs#L1629-L1734) also forwards request-derived `--compiler-bindir` and `-ccbin` into detection for non-governed CUDA families.
13. [`src/compiler/gcc.rs`](https://github.com/mozilla/sccache/blob/b799af2eea02bba9e0ef2550775fe10296b62981/src/compiler/gcc.rs#L637-L640) returns `NotCompilation` whenever the compile-only flag is absent, including source-containing compile-and-link work that does execute the compiler frontend.
14. [`src/commands.rs`](https://github.com/mozilla/sccache/blob/b799af2eea02bba9e0ef2550775fe10296b62981/src/commands.rs#L588-L612) resolves a non-absolute raw compiler selector through `which_in` before constructing the server request, while [`src/cmdline.rs`](https://github.com/mozilla/sccache/blob/b799af2eea02bba9e0ef2550775fe10296b62981/src/cmdline.rs#L203-L239) performs an earlier `which_in` plus canonicalization when the client is invoked through a compiler-named symlink. A gate at only one seam cannot prove that the client avoided search.
15. Rust accepts raw `@file` argument indirection that the pinned parser does not expand or content-hash, while the GCC parser has both its [top-level expansion](https://github.com/mozilla/sccache/blob/b799af2eea02bba9e0ef2550775fe10296b62981/src/compiler/gcc.rs#L328-L350) and a [secondary `-Xclang` expansion](https://github.com/mozilla/sccache/blob/b799af2eea02bba9e0ef2550775fe10296b62981/src/compiler/gcc.rs#L547-L583). Assembler `@file`, compiler configuration/specs, tool/wrapper selection, ambient Clang configuration, and upstream's unknown-flag pass-through add further content-indirection routes. A parser-local, Unicode-string, or finite response-file-only scan therefore cannot close the governed external-indirection class.
16. [`src/cmdline.rs`](https://github.com/mozilla/sccache/blob/b799af2eea02bba9e0ef2550775fe10296b62981/src/cmdline.rs#L299-L329) drops raw entries including `LD_PRELOAD` and `SOURCE_DATE_EPOCH` before constructing the compile request, while the pinned C hasher keys only its small `CACHED_ENV_VARS` subset. Classification after that filter cannot recover compiler-semantic bytes such as `SOURCE_DATE_EPOCH`, and hashing every surviving entry would include per-run GitHub metadata and short-lived AWS credentials that defeat cross-job reuse without closing the filtered-input hole.
17. The pinned Rust hasher keys env-dependencies reported by rustc plus selected `CARGO_*` entries, but rustc reads compiler-control state that is not a crate env-dependency. For example, [`RUSTC_BOOTSTRAP`](https://doc.rust-lang.org/unstable-book/compiler-environment-variables/RUSTC_BOOTSTRAP.html) changes feature-gate and `-Z` acceptance without appearing merely because the crate used `env!`; a C-family-only raw-environment boundary therefore leaves a governed Rust request able to cross a stale hit or accept a compile that the original environment would reject. The pinned `parse_env_dep_info` also maps an absent `# env-dep:NAME` record to an empty value, so `option_env!` can otherwise collide between unset and present-empty state.

## Required behavior matrix

| Event | Required result |
| --- | --- |
| Missing governed S3 configuration, alternate backend, disk fallback, or multilevel configuration | Fail server startup. Exactly one governed S3 backend is allowed. |
| Governed storage capability check fails, including rate limiting | Fail server startup; no read or write capability-check failure is tolerated. |
| Configured read-write storage negotiates any other mode | Fail server startup; never downgrade to read-only. |
| Parser proves the invocation performs no source preprocessing or compilation | Return dedicated `NotCompilation`, record it, and authorize intentional client execution with the original stdin and file descriptors. Source-containing compile-and-link or preprocess work is not this class. |
| `CompilerArguments::CannotCache(reason)` | Return its dedicated typed classification, record the reason, and authorize intentional client execution with the original stdin and file descriptors. The reason is telemetry, not an allowlist or policy input. |
| Source-containing GCC-family invocation lacks the cacheable compile-only shape | Return typed semantic `CannotCache` such as `compile-and-link` before `CompileStarted`; only a proven pure link or other genuine non-compilation may return `NotCompilation`. |
| Client uses compiler-named-symlink dispatch, or its explicit raw compiler selector is not an absolute byte-exact configured path | The strict derivative never enters the `cmdline.rs` symlink rewrite and fails an invocation without an explicit selector. It validates that selector before the later `commands.rs` `which_in`, `PATH` lookup, canonicalization, server connection, or client compiler execution. The exact accepted path is transmitted unchanged and independently revalidated by the server. |
| Server compiler path does not exactly match the configured path set, the detected compiler is outside the governed Rust and GCC-family/Clang set, or detection requires request-controlled identity state | Perform no per-request search, canonicalization, wrapper unwrapping, or proxy resolution. Probe only a configured exact executable under the cleared TOML-declared environment and classification deadline, then fail before request parsing, cache-key derivation, storage, or other request-specific compiler work. No request argument or environment variable reaches identity execution. Family detection does not attest that a configured executable is not a transparent wrapper. |
| Any governed raw argument has a byte-leading `@`; a C-family argument selects external configuration, tool, wrapper, plugin, or indirect assembler input without hashing the selected content; Clang lacks `--no-default-config`; or a C-family flag is not positively classified by the strict table | Return the corresponding typed `CannotCacheReason` before parsing, opening or inspecting a classified named path, starting any request-specific subprocess, or emitting `CompileStarted`; record the typed reason, perform no server filesystem or storage access, and authorize exactly one client execution with the original arguments and environment. Cacheability requires a positive proof that every argument is literal-and-keyed, content-hashed, preprocessing-captured, or inert in the compile-only shape. |
| Raw Rust or C-family environment contains duplicate names, lacks a required governed name, contains a compiler-semantic entry outside or different from its family-scoped TOML-governed set, contains interposition/search state, or contains an unclassified entry | Inspect the complete raw environment before upstream filtering. Duplicate names are fatal. Every other mismatch returns typed `CannotCacheReason::CompilerEnvironment` before parsing or compiler work and authorizes exactly one client execution with the original environment. A cacheable request keys explicit presence plus length-framed bytes for the exact governed compiler-semantic set. C strips code-proven runner metadata and credential classes; Rust forwards schema-admitted source-visible entries and keys their unset/present-empty/present-value state only when env-dep reports use, while retaining admitted `CARGO_*` keying. |
| Output target is literal `-`, `/dev/stdout`, `/dev/stderr`, `/dev/fd/*`, `/proc/*/fd/*`, or any existing destination that is not a single-link regular file—including a directory, FIFO, device, socket, destination symlink, or multiply linked regular file—or is a duplicate or colliding path | Return typed `CannotCache` before `CompileStarted`, record the reason, perform no storage operation or compilation proper, and authorize one intentional client execution. Destination type and link count are established with `lstat`; `NotFound` is the valid absent-destination state, while every other inspection error is fatal. |
| Output metadata, pinned-parent open, staging inspection, permission, space, or I/O operation fails | Fail; operational failure never becomes `CannotCache` and never authorizes client execution. |
| Compiler or evidence client cannot reach the already-running server | Fail; never auto-start or replace the server. |
| Connected server has a different derivative identity, backend fingerprint, mode, timeout policy, or frame-size policy | Fail before the requested operation. |
| Genuine cache hit | Restore the cached output successfully and succeed. |
| Governed S3 reports the object is absent | Treat this authoritative `NotFound` result as the only genuine miss. |
| Genuine cache miss in read-only mode | Compile through the server, do not attempt a cache write, and return the compiler result. |
| Genuine cache miss in read-write mode | Compile through the server and return success only after the cache write succeeds. |
| Cache read timeout/error/permission failure | Fail before launching the miss compilation. |
| Corrupt cached stdout, stderr, required output, or optional output | Fail; do not discard it or reinterpret it as absence or a miss. |
| Cached stdout or stderr member is absent | Fail as a corrupt hit; both members are required even when their decoded content is empty. |
| Strict cache write has empty stdout or stderr | Write both named members with empty payloads. The strict reader/writer format is versioned in the cache key, so permissive-format entries are unreachable. |
| Client/server EOF, other IPC error, or unexpected response | Fail; do not spawn a client-side compiler. |
| Caller sets `SCCACHE_NO_CACHE` or `SCCACHE_RECACHE` | Reject the invocation unconditionally; neither is an authorized mode in the governed build. |
| Server discovers the result cannot be cached after compilation | Return the server-owned compiler result and record it as an explicitly non-cacheable compilation. |
| Read-write cache write failure | Return failure after compilation and invalidate the job. |
| Missing, malformed, empty, or oversized abstract socket name, pathname Unix socket, TCP, or default transport selected for the strict derivative | Fail at both client and server strict entry. The governed targets have one configured Linux abstract Unix socket route and one inherited unnamed Unix-socketpair startup-notification channel. |
| Runtime timeout is zero, malformed, or exceeds the compiled-in TOML maximum | Fail at process startup before command dispatch or compiler work. |
| Compiler identity or output-discovery child exceeds the absolute classification deadline or output-byte ceiling, or its request is cancelled | A cancellation-safe supervisor that outlives the request future sends `SIGTERM` to the child's dedicated process group, waits only the governed termination grace, escalates with group `SIGKILL`, and closes its owned pipes. The unreaped group leader fences PGID reuse while a separate governed cleanup deadline enumerates Linux `/proc` membership by that PGID and treats zombie members as non-live; a process that vanishes during enumeration is absent, while malformed, unreadable, mismatched, or otherwise ambiguous identity is non-quiescent. Confirmed absence of live members permits exact-child reap and later server reuse. If live quiescence or reap cannot be confirmed within that deadline, the invocation fails, the group identity is recorded diagnostically, and one atomic poison-pending transition blocks new response commits, closes the listener, and cancels every accepted or in-flight request. A shared response-commit gate then linearizes terminal poison across all request tasks: gate acquisition, bounded frame serialization/write, connection abort, and terminal transition all refuse to wait beyond the same cleanup deadline; an already-admitted frame commits only when its final framed byte reaches the transport before terminal poison. Terminal poison occurs on gate acquisition or immediate nonzero process exit at deadline expiry, without another wait for the gate or destructors. Every uncommitted or partial `CompileStarted`, cache result, or `CompileFinished` is closed and fails. Dropping the request future or killing only the direct child is never accepted as cleanup. |
| Governed startup, absolute IPC-frame, cache-read, or required-write timeout expires, or an IPC frame exceeds the governed maximum | Fail using the adoption TOML-owned policy; the governed build has no code default or alternate environment fallback. |

The protocol must distinguish `NotCompilation` from `CannotCache(reason)`. Only those dedicated responses may reach the client-side compiler execution block. The legacy response remains distinct and fatal. EOF, IO errors, slow-drip frames, oversized frames, unexpected responses, identity mismatches, and failed or missing server connections return nonzero instead. The patch removes or makes unreachable `SCCACHE_IGNORE_SERVER_IO_ERROR` and server auto-start for compiler and evidence clients. Setup remains the sole explicit server-start path; it keeps the direct child handle until startup succeeds and terminates and reaps a timed-out child. The direct server child intentionally stays in the job's process group so job cancellation cannot leave a cache server behind; this is distinct from the dedicated per-probe groups owned by classification supervisors.

Cache-hit output handling has two phases. First, every member is decoded and validated into a temporary file created through a pinned descriptor for the destination's own parent directory; no destination is mutated during this phase. Only statically recognized path, type, link, or collision classes authorize `CannotCache`; every existing destination that is not a single-link regular file is structurally non-transactional. `lstat(NotFound)` records an absent destination that may be staged normally; every other `openat`, `lstat`, metadata, permission, temporary-file, space, or I/O failure is fatal. A duplicate is the same declared path after lexical normalization relative to the invocation working directory. A collision is either that lexical identity or the same pinned parent `(device, inode)` plus basename; an existing destination's inode and link metadata are also checked. Second, validated regular outputs are committed synchronously with descriptor-relative same-directory renames. Existing regular outputs receive same-directory backups for rollback. Parent and destination identity are revalidated before commit. The implementation has no direct-copy fallback and no worker may continue mutation after failure returns. POSIX does not provide a multi-path atomic transaction: a late commit or rollback failure is fatal, and any partial local bytes have no valid build-evidence authority.

The strict cache format is a compile-time contract. `ci/sccache-strict.toml` owns `strict_cache_format_version = "1"`, which participates in the derivative identity and is hashed as an additional common format token by both governed cache-key implementations. It does not duplicate or assume one upstream language-specific `CACHE_VERSION`. Strict writes always emit the named stdout and stderr members, including zero-length payloads; strict reads require both. A permissive-format object therefore cannot collide with a strict object even in the same bucket, and #1494 additionally adopts a fresh strict prefix so read-only rollout never depends on warm permissive entries.

The server starts only when the effective backend and mode exactly match the governed S3 configuration. Read-only mode skips `put` entirely. Read-write mode withholds success until `put` completes. The patched binary requires typed startup, IPC, cache-read, required-write, abstract-socket, canonical compiler-path/family, governed family-scoped compiler-environment, and maximum-frame inputs but does not own their consumer values; #1494 supplies them from `ci/sccache-location.toml`. The code-owned compiler-environment schema fixes the semantic categories and cannot be changed by adoption config; #1494's TOML map supplies only the exact secret-free byte values for entries the schema classifies as governed compiler inputs. Its loader rejects duplicate names, names outside that category, credential-class names, malformed bytes, and values that cannot be represented by the typed Unix-byte input. The canonical map and schema revision participate in the handshake identity. `ci/sccache-strict.toml` owns `max_runtime_timeout_ms = 3600000`, the Linux abstract-name byte limit, and one grouped classification contract: the governed compiler set, `classification_timeout_ms`, `classification_termination_grace_ms`, `classification_cleanup_timeout_ms`, `classification_output_max_bytes`, and `identity_probe_environment = {}`. These values are compiled into the derivative and its identity. The loader accepts only the empty probe-environment table, requires both cleanup intervals to be positive and smaller than the classification timeout, and requires the checked sum of classification, termination grace, and cleanup to fit the compiled runtime maximum; it has no response-file reason string to validate because typed `CannotCacheReason` variants own those semantics. The child environment is cleared before the exact configured executable is invoked, so no request or host environment is inherited. `classification_output_max_bytes` bounds combined stdout plus stderr per process group, with capacity reserved against one shared counter before either buffer grows. The supervisor owns the unreaped group leader, pipes, termination grace, escalation, stable live-membership check, exact-child reap, cleanup deadline, and atomic daemon-poison transition independently of the cancellable request future. Cleanup-bound exhaustion is a fatal daemon-poison state, not a recoverable request error; listener, accepted-connection, response-writer, and in-flight request tasks share the terminal state and cannot emit authority after it. Response-gate acquisition, every bounded frame write, socket abort, and terminal process exit checks the same cleanup deadline before and after every await or write; inability to complete the transition by that deadline invokes immediate nonzero process termination rather than another wait. All four consumer timeouts are parsed once and must be positive and no greater than the runtime limit. An opaque `Deadline` type is the only strict-runtime interface accepted by startup, IPC-frame, cache-read, required-write, classification-child, termination-grace, cleanup, response-commit, and retry helpers; its checked constructors own all `Instant` addition and retry/backoff multiplication and expose no unchecked arithmetic. Classification readers enforce their combined byte ceiling before allocation or growth. The strict path has no built-in operational defaults.

## Build and publication flow

1. A pull-request build checks out and asserts the actual PR head SHA; a manual build checks out and asserts the dispatched exact-current-main SHA. It downloads the exact source archive and verifies its SHA-256 before extraction.
2. The canonical recipe extracts outside the enclosing repository, requires a non-empty zero-context patch file list, runs `git apply --unidiff-zero --check`, applies the patch, and proves the resulting tree accepts the exact reverse patch. The source archive digest supplies the exact context boundary; zero-context storage keeps the committed patch diff-clean. A skipped, empty, or wrong-source application is fatal.
3. The workflow builds the debug binary required by the upstream library harness, then runs the complete upstream library suite before the release build.
4. Dependency acquisition is checksum-locked. The build then runs network-disabled with fresh Cargo and target directories, no wrapper or incremental compilation, and an explicit normalized environment and path remapping.
5. Two isolated jobs build each architecture with the same verified source, patch, toolchain, container digest, features, and build settings.
6. Each builder verifies the expected ELF architecture, absence of a runtime interpreter and shared-library dependencies, and host execution outside the build container. Separate scrubbed-environment controls prove that missing S3 configuration, an injected disk backend, missing/empty/oversized abstract names, pathname sockets, TCP, default transport, and oversized runtime timeouts fail at strict entry with their distinct diagnoses. The positive strict-server control uses a unique Linux abstract socket and leaves no filesystem socket entry.
7. Builder jobs upload binaries and a provenance manifest as same-run, same-attempt artifacts bound to the exact head, run ID, architecture, configured replica, toolchain, container, source, patch, workflow, and canonical recipe. Attempt-qualified artifact names prevent a re-run from reusing or colliding with an earlier attempt. Builders have `contents: read` only and no cache or publisher credentials.
8. An unprivileged verification job runs for pull requests and dispatches, independently hashes all four candidates, validates every manifest binding, requires byte equality per architecture, and emits one attempt-qualified verified bundle. A protected publisher is never required to learn whether the replicas agree.
9. The publisher runs only for `workflow_dispatch` whose SHA is observed as exact-current `main`, uses the one TOML-owned publisher environment name emitted by unprivileged preflight as both the job's `environment:` expression and every environment API predicate, and receives job-scoped `contents: write`. The same TOML-owned GitHub API version governs every request. Unprivileged preflight uses the verifier driver's standard-library HTTP client rather than an unpinned host CLI and validates the repository owner, name, and numeric ID for later canonical pagination. Checkout does not persist credentials. The publisher token is removed from the environment before repository-controlled verification code runs and is supplied only to individual invocations of the verified absolute GitHub CLI path. The publisher does not execute Cargo, build scripts, or the produced binaries.
10. A tokenless publisher-preparation step downloads only the verified bundle from its own workflow run, reruns the same manifest and byte verifier, and requires byte-identical verifier output. It downloads the exact TOML-pinned GitHub CLI archive for the publisher target into a fresh exclusive `RUNNER_TEMP` directory, verifies the archive SHA-256 before extraction, validates the absolute executable's version and required `api`, `release verify`, and `release verify-asset` capabilities, and exports only that absolute path. No publisher command resolves `gh` through `PATH`; every token-bearing API or release invocation quotes the verified absolute path. The release tag is derived from the full SHA-256 of the canonical governed build-input identity, including source, patch, executor, toolchain, workflow, recipe, replica set, build settings, verification threshold, publisher configuration, and targets.
11. The token-bearing release step confirms observed-current `main` and the protected environment, then atomically creates the exact tag with `POST /git/refs`; only a direct `201` whose response body identifies the exact full ref, commit object type, and commit SHA is success, followed by an exact ref/SHA readback. A collision, timeout, lost response, wrong body, wrong readback, or any other ambiguous result fails and preserves the tag state for operator review. It generates a run/attempt/head ownership marker, creates a draft bound to the already-created tag, validates the returned exact release ID and mutable draft state, and uploads the agreed binaries and provenance.

   Cleanup has exactly two modes. When a create response returned an ID, known-ID cleanup uses only `GET /releases/{id}` and may delete only that exact owned object. When the response was lost, unknown-ID recovery performs one TOML-bounded release census. Every continuation URL must be previously unvisited and same-origin; its path must be either `/repos/{owner}/{repo}/releases` or GitHub's canonical `/repositories/{repository_id}/releases`, with the numeric ID bound to the repository identity validated by preflight. Decoded query parameters must preserve the governed page size exactly once, allow only one changing positive page cursor, and reject every other key. Recovery requires exactly one global match by repository, run, attempt, head, tag, target, and ownership marker before binding its numeric ID. Matches split across pages or any detectable ambiguous, malformed, cyclic, or truncated census preserve state and fail. The releases endpoint exposes no `total_count`, so a well-formed but silently short or visibility-lagged listing is an accepted platform residual: recovery preserves the unobserved object, and the atomically reserved tag makes a later dispatch fail loudly without granting adoption authority. In either mode, cleanup requires `immutable` to be exactly `false`, may delete the exact mutable release whether it is still a draft or was published without immutability, and never automatically deletes a Git tag. Deletion must be confirmed or definitely absent before any later cleanup mutation. Failed or ambiguous release deletion stops all later cleanup mutations.
12. Every byte, manifest, release identity, current-`main` observation, environment predicate, downloaded-asset comparison, and pinned-GitHub-CLI capability check that can be performed before publication is checked while the release is still a draft. The publisher then revalidates current `main` and the environment immediately before publishing. Publication is a one-way transition only when GitHub applies immutability: GitHub automatically creates the release attestation for an immutable release, and the workflow must read back `immutable: true`, recheck `main`, and use bounded TOML-governed polling with the digest-verified GitHub CLI for `gh release verify` and `gh release verify-asset`. If `main` moves or any post-publication predicate fails after immutability is confirmed, the immutable candidate is retained without adoption authority and the workflow fails. It is never deleted automatically; a corrected derivative uses a new content-derived tag. If publication instead yields an exact owned mutable release, cleanup removes only that numeric release ID and preserves the reserved tag for operator review. A following tokenless step evaluates the exact release/tag/asset predicate. The later consumer still verifies its independently reviewed SHA-256 pin.

The repository owner must enable release immutability and create the main-restricted publisher environment before the first publication dispatch. The immutability-settings endpoint requires repository Administration-read permission, which is not an available `GITHUB_TOKEN` workflow permission. The design therefore adds no second credential: an administrator verifies the setting as protected-environment approval evidence before the first dispatch, while the workflow verifies the environment before publication and the exact immutable result immediately after publication. A disabled or raced setting may publish an exact owned mutable release before the readback exposes it; the workflow removes only that release by numeric ID, preserves the atomically reserved tag, fails the dispatch, and grants no adoption authority. These operator prerequisites do not belong to the prerequisite PR's diff. GitHub documents that immutable release assets and their tag cannot be changed after publication, that immutable publication automatically generates the release attestation, and recommends draft, upload, then publish: [Immutable releases](https://docs.github.com/en/code-security/concepts/supply-chain-security/immutable-releases), [Immutable-release settings API](https://docs.github.com/en/rest/repos/repos#check-if-immutable-releases-are-enabled-for-a-repository), [workflow token permissions](https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-syntax#permissions), and [Verifying release integrity](https://docs.github.com/en/code-security/how-tos/secure-your-supply-chain/secure-your-dependencies/verify-release-integrity).

## Trust boundary

- Repository review owns the upstream commit, source digest, patch, build recipe, and publisher workflow.
- Builder jobs are unprivileged and cannot publish or write the compilation cache.
- The publisher token can create releases and modify unprotected refs. Native protected-`main` governance, required review, and the separate #1494 change prevent those capabilities from activating a binary.
- #1494 makes `ci/sccache-location.toml` the sole install authority by independently pinning immutable release ID, per-architecture asset IDs, and binary SHA-256 values after publication. Build-provenance TOML does not duplicate those install facts.
- PR and main cache roles cannot publish or replace the executable.
- A compromised publisher can create an unwanted release, but cannot activate it without a separate reviewed adoption change.
- Release deletion or GitHub unavailability intentionally stops installation; there is no S3, upstream-release, preinstalled-tool, or local-build fallback.

It also owns behavior evidence that Cargo's supported compiler invocations cannot silently bypass the governed wrapper and positive evidence from the real governed build that representative Rust and C-family requests reach `Cacheable`, classification telemetry contains no unexplained dominant fallback, and otherwise-identical invocations in distinct jobs produce at least one genuine cross-job hit despite different GitHub run metadata and short-lived AWS credentials.

## Accepted residual risks

- Explicitly classified `NotCompilation` and `CannotCache(reason)` invocations, including non-transactional output destinations, execute on the client by design. Their prior server classification and persisted statistics are the governance evidence; the strict binary does not claim daemon ownership of those processes.
- Linux abstract Unix sockets remove pathname-socket support from the governed derivative. This matches the two published Linux targets and intentionally makes macOS execution non-authoritative.
- Cache entries from the permissive format and prefix are intentionally not reused. Strict reader/writer agreement and adoption correctness take priority over warm-cache hit rate.
- Response-file invocations in every governed compiler are intentionally never cacheable. Clang without explicit default-config suppression and every unproven C-family external config/tool/wrapper/plugin indirection is likewise classified non-cacheable. Unknown C-family flags default to that safe class. These invocations execute only after the server records the explicit typed classification, and the server never opens or expands their classified named files; this deletes uncancellable blocking-filesystem and silent under-hash paths rather than claiming an in-process deadline can bound them.
- Exact-path matching and cleared probes remove request-controlled selection and establish compiler family, but a finite probe cannot attest that the configured executable is not a transparent wrapper or proxy. #1494's reviewed canonical-real-path configuration owns that supply identity; the derivative handshake binds the exact configured path and policy rather than claiming independent content attestation.
- The governed family-scoped compiler environment binds exact compiler-semantic values but cannot attest that a subordinate tool at an unchanged governed search location was replaced during the job. #1494's controlled job/toolchain environment owns that immutable-supply assertion; a compromised configured compiler or toolchain remains within the already-declared shared-input compromise risk.
- A raw Rust or C-family environment entry outside the code-owned schema, a missing or different TOML-governed value, rustc control not separately keyed, or interposition/search state intentionally makes the invocation non-cacheable. The pinned Rust env-dep and admitted `CARGO_*` hashing remain defense beneath the common schema but never authorize an otherwise-unclassified rustc environment read. Code-proven GitHub runner metadata and credential classes are removed from C-family compiler execution and keys; schema-admitted Rust source-visible values are forwarded and enter the key only when dep-info reports use, preserving exact `env!` semantics without making normal per-run rotation destroy cross-job reuse. Unknown state degrades to explicit client execution rather than silent key churn or under-hashing.
- A process-group member stuck in uninterruptible kernel sleep may survive `SIGKILL` past the governed cleanup deadline. The invocation fails and the atomically poisoned daemon closes its listener and all accepted connections, cancels in-flight authority, and exits nonzero; it never waits indefinitely, returns later success, or reports reusable quiescence. The leaked kernel task is loud job-level evidence loss, not valid compile or cache authority.
- An abstract socket name is local coordination, not authentication. The mandatory derivative/configuration handshake rejects accidental stale or upstream servers; a malicious same-user process able to kill and impersonate the governed daemon is outside the one-person agent-error threat model.
- POSIX cannot make a multi-output commit atomic. No output is touched before complete staging and validation, but an unrecoverable late commit or rollback failure may leave partial local bytes. The invocation fails and those bytes have no evidence authority.
- Descriptor-relative output operations prevent accidental parent-path replacement from redirecting a commit. They do not defend against a malicious same-user process mutating the pinned directory concurrently; that actor is outside the one-person agent-error threat model.
- Destination `lstat` does not canonicalize every ancestor symlink. Pinned-parent identity and pre-commit revalidation prevent accidental redirection at the governed seam; adversarial same-user namespace mutation remains outside the threat model.
- A required read-write cache write can fail after compiler outputs exist locally. The invocation and job still fail, so those outputs have no valid evidence authority.
- The binary contract begins when an invocation enters the governed wrapper. #1494 owns the job-level routing claim; an arbitrary process that never invokes the wrapper is outside this prerequisite's evidence boundary.
- Both replicas share the reviewed source, dependencies, toolchain, container, and runner provider. Byte equality does not detect an identical compromise in a shared input.
- GitHub archive or release unavailability, release deletion, or a changed auto-generated source archive stops the build or installation intentionally.
- An ambiguous tag-create or draft-cleanup result can reserve the content-derived tag and require operator review. The workflow never trades evidence integrity for automatic retry.
- The release-list endpoint exposes no `total_count`. A well-formed but silently short or visibility-lagged unknown-ID recovery census can miss an owned mutable release; the workflow preserves state, the reserved tag blocks a blind retry, and no missed object receives adoption authority.
- Automatic immutable-release attestation timing is undocumented. Bounded governed polling may fail after publication and leave an immutable but unadopted candidate; a corrected derivative receives a new identity.
- Publisher configuration participates in the content-derived release identity. Rotating the pinned GitHub CLI or API version can intentionally create a new tag for byte-identical binaries; permanent tag retention favors auditable identity over namespace reuse.
- Every upstream sccache upgrade requires a fresh source pin, patch review, behavior matrix run, reproducible publication, and adoption change.

## Failure and recovery

Any verification, build, reproduction, environment, release, download, or digest failure stops the affected workflow. An exact owned mutable release may be removed by numeric release ID whether it is still a draft or was published without immutability; deletion must be confirmed before any later cleanup mutation. Git tags are never removed automatically. An immutable result is retained for review even if later evidence retrieval fails. A fix produces a new content-derived release identity. There is no fallback publication or installation channel.

Upgrades use a new reviewed upstream commit, source digest, rebased patch, immutable release, and adoption PR. Historical releases are retained but still depend on GitHub availability and the release not being deleted. Emergency revocation pauses affected CI or adopts a new immutable release; it never mutates an existing asset or restores the official permissive binary.

GitHub's reference-deletion endpoint has no expected-SHA or conditional precondition, so automatic tag deletion is deliberately excluded. Ambiguous or orphaned tags are operator-review states, never cleanup targets. See [Git references REST API](https://docs.github.com/en/rest/git/refs).
