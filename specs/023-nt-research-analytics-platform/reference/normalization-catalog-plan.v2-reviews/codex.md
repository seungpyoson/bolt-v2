Findings:
- [critical] F15: canonical bytes are written before pointer CAS, but NT ignores the pointer (specs/023-nt-research-analytics-platform/reference/normalization-catalog-plan.v2.md:315-337)
  The promotion flow writes each object to canonical nt-catalog/ before the artifact-index pointer CAS, then claims canonical reads resolve only through the committed pointer/snapshot. Pinned NT query_files builds data/<type> with make_path and recursively lists the object-store prefix; BacktestNode dispatches directly to catalog.query. It has no artifact-index pointer awareness. A failed/lost CAS after PutMode::Create leaves objects under a canonical NT-readable prefix, so direct catalog reads can consume orphan or superseded bytes despite the pointer state.
  Recommendation: Do not write into a shared canonical NT catalog prefix before commit. Commit immutable snapshot/package roots, then expose only the committed root to NT, or materialize a clean NT-compatible catalog from the committed package after pointer CAS.
- [high] F2: hash-keyed filenames break NT interval selection and can double-read transforms (specs/023-nt-research-analytics-platform/reference/normalization-catalog-plan.v2.md:280-287)
  v2 makes content_hash/transform_hash part of the NT-visible parquet filename. At pinned NT 6e059dc, the writer's canonical filename is exactly timestamp_timestamp.parquet and query filtering parses filenames by splitting once on '_' and parsing the second half; if parsing fails, the file is treated as intersecting every requested range. Inference from NT catalog.rs:4595-4600 and 4626-4638: v2's '__t-...__c-...' suffix makes these files unparseable, so BacktestNode/query_files can include all hash-suffixed objects in a directory, including multiple transforms for the same interval.
  Recommendation: Keep NT-visible filenames in NT's timestamp_timestamp.parquet format and isolate alternate transforms in immutable package/snapshot catalog roots, or require a reader that consumes an exact manifest instead of recursive NT prefix listing.
- [high] F14: proof-first rule is contradicted by pending-proof NT staging (specs/023-nt-research-analytics-platform/reference/normalization-catalog-plan.v2.md:399-407)
  v2 states no source data may enter an NT-replayable catalog path until SourceProofReport status and nt_mapping_status are accepted, but the next section allows 'normalized tables + an NT catalog' under non-canonical staging with a provisional source_proof_id. That is not class-level prevention; it creates an explicit pending-proof provider-byte path into NT layout and relies on later humans/tools not to point BacktestNode at it.
  Recommendation: Remove NT catalog generation from interim staging, or restrict it to Tier C non-NT research tables. Add a manifest/catalog validator that rejects v0-pending or non-accepted proofs under any Tier A/B NT prefix and before any BacktestResult is emitted.
- [high] F7: live write_mode gate still accepts drift and rejects the proposed replacement (scripts/backfill_coverage_ledger.py:286-293)
  v2 says write_mode has exactly dry_run/local_staging/canonical_s3 plus staging_location, but the live ledger treats any manifest with payload keys and write_mode not in ('local_staging','dry_run') as accepted. That accepts old values, typos, and unset modes while the proposed local_staging + staging_location=s3_noncanonical manifests would be excluded. Live producers still emit s3_staging, e.g. backfill_accept_staged_objects.py:209 and backfill_hyperliquid_hip4_to_s3.py:762.
  Recommendation: Migrate producers and ledger atomically: validate write_mode against the three-value schema, require staging_location for local_staging, count only local_staging+s3_noncanonical as S3 staging, and reject unknown or missing modes.
- [high] Orphan raw uploads can be accepted from key paths without a source manifest (scripts/backfill_accept_staged_objects.py:151-209)
  The new --from-s3-keys path builds an acceptance manifest for every content-addressed object under a raw prefix, explicitly for orphaned uploads whose run never wrote a manifest. It reconstructs provenance from path segments, makes source_proof_id optional, and verifies only a sample by default. That can turn unmanifested/orphan bytes into accepted-binding coverage, undercutting the plan's claim that orphan/superseded bytes cannot be promoted or trusted.
  Recommendation: Require a source manifest or an explicit owner-approved orphan recovery record with mandatory accepted source_proof_id, full hash verification, complete provenance validation, and a distinct recovered_orphan state that is not counted as accepted until reviewed.
- [medium] F8: provisional v0 source proof ids conflict with the proof schema (specs/023-nt-research-analytics-platform/reference/normalization-catalog-plan.v2.md:526-532)
  v2 defines provisional ids ending in ':v0-pending' and says that segment maps to source_proof_version. The source proof schema requires source_proof_version to be a positive integer. If v0 is emitted as a SourceProofReport version it is schema-invalid; if no report exists for v0, staged rows point at a proof id the acceptance gate cannot resolve.
  Recommendation: Use a positive version even for pending proofs, such as v1 with status=pending, or separate provisional row ids from source_proof_version and require a resolvable pending SourceProofReport record.
